# Changelog

This file records every notable change to GrokChat: what changed, and why. It follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions will follow [Semantic Versioning](https://semver.org/) from the first release to `main`.

## [Unreleased]

### Fixed

- **Replies only to the account's own posts; a refused reply never disconnects the account** (GROKCHAT-17, incident 2026-10-28):
  - `create_post` and `create_thread` refuse an `in_reply_to` that is not a post the same account published through GrokChat with **`reply_target_not_own`**, before anything is stored or audited (port `OwnXPosts`, D1 and memory drivers on the post store's contract suite). `edit_post` has no reply field. A reply stored before the rule is never sent: it ends FAILED with `reply_target_not_own` without an X call;
  - **a 403 on a create sent as a reply** (part 1 of a reply, or a thread's later part) ends the post FAILED with `reply_refused`, keeps the account ACTIVE and is not retried; a 401 is still a reconnect, and a 403 on an original post is unchanged;
  - every failed create's audit `detail` now carries X's status and wording (`<outcome>: x_<status>: <detail>`, redacted, at most 300 characters of X's detail), not just the outcome's kind;
  - the tool descriptions, the setup prompt, the plan (§16) and the runbook (§11) say to reply only to the account's own posts and to draft other replies for a person to post by hand;
  - **Why:** X allows API replies only to the account's own posts or to people who engaged with it. Replies to `@XDevelopers` and `@clavicular` came back as 403s whose wording the content check missed, so they were read as auth failures: the account was disconnected, and after each reconnect the same post retried and disconnected it again, five times. The owner judged that a repeat risks a ban.

### Added

- **Bots upload their own images** (GROKCHAT-20):
  - MCP tool **`upload_media`** (15 tools): a bot sends a PNG, JPEG, WebP or GIF it made in its own workspace as base64, in one call or in parts of at most 256 KiB decoded, each with its own SHA-256 and the whole file's SHA-256. A garbled part is refused at once with `part_hash_mismatch` naming the part, so only that part is resent; resending a part is idempotent. When every part is in, the file is assembled, its hash checked (`file_hash_mismatch`) and stored through `MediaIntake` with the new source `bot_upload` (magic bytes, X's limits, the R2 quota guard, the same cleanup), audited as `media.bot_upload`; it returns `media_id` for `create_post` / `create_thread`;
  - scoped to the token's person's accounts; other refusals: `bad_base64`, `part_out_of_range`, `part_too_large`, `upload_not_found`, `upload_expired`, `upload_mismatch`, `not_media`, `too_large`, `media_quota`, `invalid_label`, `scope`, `not_found`;
  - **no migration**: unfinished uploads' parts sit in R2 under `uploads/` (port `PendingUploads`, memory and R2 drivers on one contract suite), expire after an hour, and the metrics tick deletes them inside its budget (`UploadCleanup`, run after the staged-media cleanup by `CleanupSteps`);
  - `list_media` and the Media page show the `bot_upload` source; the tool descriptions, the setup prompt, the plan (§17) and the runbook (§10) explain when to use `upload_media` and when `stage_media_from_url`;
  - **Why:** Grok bots render images in their workspace with no public link, and the sandbox has no outbound network, so the only way out for the bytes is the MCP tool call itself.

- **Images for bots** (GROKCHAT-18):
  - **Grok's image host is allowed**: `GROKCHAT_MEDIA_HOSTS` is `imgen.x.ai`, so a Grok-generated image link stages with `stage_media_from_url` and posts. Every fetch protection stays (https, exact host match, every redirect re-checked, no literal IP, size caps, magic bytes);
  - **a host refusal says what to do**: `host_not_allowed` carries a `message` naming the allowed hosts (or that none is set) and pointing at the dashboard upload;
  - **the dashboard's Media page**: upload a PNG, JPEG, WebP or GIF for one account with an optional label (photos up to 5 MB, GIFs up to 15 MB, the type read from the bytes), stored like staged media under the R2 quota guard and the same cleanup; each account's recent media with a thumbnail served same-origin behind the session, its `media_id` to copy, used or unused and when it expires; Delete for unused media. Uploads, deletes and refusals are audited. Only that POST takes a body past 64 KB;
  - MCP tool **`list_media`** (read-only, scope-checked, 14 tools): an account's staged media with `media_id`, `label`, `content_type`, `bytes`, `uploaded_at`, `source`, `used` and `expires_at`, unused by default, so a bot finds an upload by itself; `create_post`'s description and the setup prompt explain both image routes;
  - migration `0006_media_labels.sql`: `staged_media.label`, `staged_media.source` and the `staged_media_owner` index; port `MediaCatalog` (D1 and memory drivers on one contract suite);
  - **GROKCHAT-16 leftovers**: the token panel wraps on a phone, and the token form carries a one-time nonce spent in one conditional write (`PersonRepository.replaceToken`), so a reload or a double send never rotates the token again; a stale form asks before rotating;
  - the setup prompt's intro no longer says GrokChat cannot reply (GROKCHAT-17 added replies);
  - **Why:** a bot could not attach a banner: every URL was refused, the refusal did not say why, and a bot cannot upload a local file at all (Grok's sandbox has no network).

- **Replies to other people's posts over MCP** (GROKCHAT-17):
  - `create_post` and `create_thread` take an optional **`in_reply_to`**: an X post id or the post's URL (`https://x.com/<handle>/status/<id>`, twitter.com and mobile hosts too). Part 1 is sent as a reply to it; a thread's later parts chain under it as before. A target that is neither is refused as `reply_target_invalid`;
  - everything else works as for an original post: media, `publish_at`, review mode, the gate (caps, gaps, quiet hours, link policy), idempotency, metrics, edit, cancel and delete. The target is part of the request hash, so the same key with another target is refused as `idempotency_mismatch`; an original post's hash is unchanged, so stored hashes still match;
  - the post keeps its target (`posts.reply_to_x_post_id`, nullable, migration `0005_post_replies.sql`); `get_post`, `list_backlog` and the edit/cancel/delete results show it as `in_reply_to`, and the dashboard's post page links it ("Reply to");
  - a 403 from X saying a reply to this conversation is not allowed (the author has not mentioned or engaged with the account) is a content refusal: the post is rejected and the account is **not** marked as needing a reconnect;
  - the tool descriptions and the setup prompt tell the bot how to reply;
  - **Why:** the owner wants bots to reply to other people's posts with the same features as original posts.
